# ADR-0002: Git as the Operational Source of Truth

- **Status:** Accepted
- **Date:** 2026-10-14
- **Supersedes:** [ADR-0001](ADR-001.md)
- **Tags:** architecture, gitops, privacy, career-as-code

## Context

OpenCareerOps v0.1 already validates a versioned JSON career snapshot and generates a deterministic weekly report. The previous operational source-of-truth decision (Notion) introduced an external data dependency without adding value to this working flow. The project is public, whereas real career records can be sensitive.

## Decision

Use Git as the sole operational source of truth, with explicit separation of concerns:

- **Public `OpenCareerOps`:** code, input contract, examples with fictional data, tests, architecture decisions and its quality gates.
- **Private `career-state`:** the canonical `state/current.json` on `main`, reviews through PRs, and Git commit history. Generated Markdown reports are derivatives, not authoritative state.
- Use the existing JSON schema version 1; validate it and run the same Python engine in both CI and locally.
- CI may read the private state and create a temporary weekly report artifact, but must not push, publish, or change career data automatically.
- No Notion synchronization or automatic migration. Existing Notion records remain historical references, not a live source for the application.
- Keep human approval of career changes and recommendations; do not automatically apply recommendations.

## Consequences

**Benefits:** one reviewable history of state changes, no external database/API or credentials, clear reproducibility with a pinned engine commit, and reuse of existing CI and engine.

**Costs/trade-offs:** editing JSON is less convenient than a UI; history is commit-based rather than event-oriented; reading/queries across large career datasets would be cumbersome; scheduling on GitHub Actions is best-effort rather than precise.

**Security and privacy:** the operational repository MUST be private before real data is committed. Git encryption at rest on a host is not a replacement for repository access control; do not commit API keys, passwords, access tokens, personal identification numbers or unnecessarily sensitive information. Treat Git history and workflow artifacts as persistent copies; deleting a file from a new commit does not erase it from history. GitHub Actions should use `contents: read`, avoid printing report content, and keep artifacts short-lived. Use branch protections if available on the private repository.

## Revisit when

Cross-source queries, concurrent edits, retention/deletion requirements, non-Git contributors or verified evidence show a database would materially improve the workflow. Introduce such complexity by a separate ADR and with an explicit migration plan.
